## State at opening

The complete v0.7 scope was re-verified on this date on the unchanged v0.7.11 implementation:
Ruff clean, mypy clean over 42 source files, all 301 tests passing and a clean wheel build. The
formal completed-v0.7 review (`docs/implementation_report_v0.7_review.md`) stands, and the

## What v0.8 is

A read-only presentation layer over verified run manifests. It renders results the validated
domain modules have already produced and recorded; it computes nothing, transforms nothing and
decides nothing. The one sentence that governs every design choice below:

> **A report renders verified manifests, and only verified manifests.**

The manifest is the sole doorway. A number that never passed through
`greek_bess.reporting.read_run_manifest` — with its schema-version check, closed kind registry,
basis cross-check, guaranteed-key check and scoped distributional-term refusal — cannot appear
in a rendered report. This is what makes the presentation layer thin by construction rather
than by discipline: every integrity property the contract enforces is inherited, not restated.

## What v0.8 deliberately is not

- **Not a computation surface.** No dispatch, forecast, transformation, finance or degradation
  call is reachable from the renderer. It cannot re-run anything; it can only read what a run
  recorded.
- **Not a server.** The core deliverable is a deterministic CLI (`render-report`) producing
  self-contained static files. Nothing listens on a port, nothing requires a browser session to
  produce evidence, and CI can validate every rendering path without secrets or network access.
- **Not a new dependency.** The core renderer uses the standard library and the packages the
  project already carries. A Streamlit or comparable interactive viewer is explicitly deferred
  to its own decision (see "Deferred" below): the suggested branch sequence's
  `streamlit-dashboard` label predates the 2026-08-27 repositioning as a replay and research
  benchmark, and a static exportable report is what that repositioning actually needs first.
- **Not an AI-explanation layer.** The `ai-explanations` item in the suggested branch sequence
  remains outside v0.8 entirely.

## The three questions the gate required a design to answer

### 1. The landing state, when no judgmental input has been declared

Every judgmental input in this project has no default, by recorded decision: the bootstrap
source era, the spread-compression factor and reference basis, the availability baseline, the
negative-price event list, the scenario set of an ensemble. An interface must render something
before any of them is declared, and whatever it renders becomes the de facto default.

**The landing state is the declaration record, not a result.** Invoked with no manifests,
`render-report` produces a report whose body is the project's declaration checklist: each
judgmental input that has no default, the dated decision that made it default-free, and the
command that records a result once the declaration is made. It contains no figures, no example
numbers and no synthetic demonstration. A blank page would be unhelpful; a demo with implied
defaults would silently settle every trade-off the decision log refused to settle; the checklist
is the honest third option — a refusal with instructions.

### 2. How every rendered figure carries its label and the standing exclusions

`PROMPT.md` requires outputs to retain their source and limitation labels through downstream
analysis, and a rendered report is downstream analysis.

- Every figure is rendered inside a block that displays, adjacent to the figure and not in a
  global footer, the manifest's `result_label`, its `basis` in reader-facing words (a
  perfect-foresight ceiling, a settled backtest, a synthetic scenario, screening arithmetic,
  data-acceptance evidence) and the three `standing_exclusions` the manifest carries.
- The label is read from the manifest, never re-declared by the renderer, so it cannot drift
  from the summary the producing module wrote — the same one-source-of-truth rule the contract
  itself follows.
- Figures of different bases are never merged into one table row, total or derived value. A
  report may place a replay ceiling and a scenario range on the same page; it may never add,
  subtract, average or ratio them, because the result would be a number whose basis is none of
  the five the contract defines.
- A manifest that fails verification is refused with the contract's own error, and the report is
  not produced. There is no partial render: a report that silently omitted a failing manifest
  would present the remainder as the whole.

### 3. What an export refuses to contain

An export is the artifact most likely to travel beyond a reader who knows this project's
limits, so the refusals are executable, not stylistic:

- **Any figure not reachable from a verified manifest.** The renderer's only numeric input is
  the manifest list; there is no side channel for a caller to inject a value.
- **Interval-level official price series.** Manifests carry the producing module's summary —
  aggregates and declared configuration — and the renderer reads nothing else, so official
  HEnEx/ENTSO-E interval data cannot enter an export by construction. This keeps the
  redistribution question that forced encrypted custody entirely out of the export path.
- **Distributional vocabulary where the kind forbids it.** For manifests whose kind declares
  `forbids_distributional_terms`, every rendered heading, caption and key the renderer emits
  for that block is checked against `FORBIDDEN_REPORT_TERMS`, and a match raises instead of
  rendering — the same executable exclusion the ensemble and the contract already enforce.
- **An unlabeled figure.** Unreachable if the contract holds; asserted anyway by a regression
  test that renders every registry kind from a real summary and checks the label's presence in
  the output.
- **Secrets and environment.** The renderer reads no environment variables and makes no network
  request; there is nothing for it to leak.
- **A probability, percentile, expected value, ranking or central case across scenarios or
  paths** — not as a rendering choice but because no verified manifest can carry one.

Exports are generated research outputs and therefore stay outside Git, under the existing
repository contract; the report renderer writes below ignored output directories exactly as
every other CLI command does.

## Rendering contract

- **Input:** one or more run-manifest JSON files, each read through `read_run_manifest`.
- **Output:** one self-contained HTML file (no external assets, scripts or network fetches) and
  a machine-readable index JSON naming every manifest rendered, its kind, basis, label and
  digest — so a report is auditable back to the exact manifests behind it.
- **Determinism:** identical manifest inputs produce byte-identical report bodies. Manifest
  ordering in the report follows a declared sort (basis, then kind, then manifest ID), never
  input order. The report records the digest of each input manifest; the only timestamp the
  renderer itself adds is `rendered_at_utc` in the index, following the manifests' own
  `recorded_at_utc` precedent.
- **Grouping:** the report is organised by basis, in the order the contract declares them, so a
  reader meets the ceiling/backtest/scenario distinction as the structure of the document
  rather than as a footnote.
- **Kind-aware sections:** kinds with guaranteed summary keys beyond `result_label` (the
  dispatch margins, the ensemble's scenario names, finance's operating-margin case) render
  those keys as their section headline; everything else in a summary renders as the recorded
  key-value detail it is, without reinterpretation.

## Milestones

- **v0.8.0 — Report rendering foundation.** `render-report` CLI and
  `greek_bess.reporting.render` module: verified-manifest input, the landing state, per-figure
  label blocks, basis grouping, the export refusals above, deterministic self-contained HTML

  byte-determinism.
- **v0.8.1 — Multi-run composition.** An index page across many manifests, side-by-side

  explicit rendering of the equivalent-basis evidence the ensemble records. Composition remains
  layout only: nothing is computed across manifests. **Landed 1 September 2026**; see
  "Amendment" below and `docs/implementation_report_v0.8.1.md`.
- **v0.8.2 — Interactive viewer decision.** A separate dated decision on whether a local
  interactive viewer (e.g. Streamlit) is added *on top of* the static renderer. It would be a
  new runtime dependency and a new rendering surface, and it is not needed for exportable
  reports, so it is not assumed. If declined, v0.8 completes with the static renderer.

Each milestone is one reviewable PR through the standard workflow and gates; version numbers
bump when implementation lands, so the package stays at 0.7.11 until v0.8.0 merges.

## Amendment, 1 September 2026 — where the ensemble's per-path ranges live

This document is the design of record and changing it requires a dated decision entry. One was
required by v0.8.1 and is recorded in `DECISIONS.md` as *"Record the ensemble's per-path ranges
in its summary, rather than reading its CSV"*.

The tension: v0.8.1 requires a scenario ensemble to be shown with its per-path ranges, and those
ranges lived only in the CSV `report-scenario-ensemble` writes. The run summary a manifest
carries held the scenario list, the equivalent basis, the path count and four extreme
aggregates. The manifest is the sole doorway, so reading the CSV was never an option — it would
have broken the one sentence this whole layer rests on, and a figure taken out of a CSV arrives
stripped of the label the manifest carries.

The resolution is that the **producing module records what a report may show**, rather than the
report reaching past the manifest for it. `report_scenario_ensemble` now records `path_ranges`
in its summary: a per-path projection of the same frame the CSV is written from, in the same
order, with nothing rounded, converted or re-reduced. `scenarios`, `equivalent_basis`,
`path_count` and `path_ranges` become guaranteed summary keys of the `scenario_ensemble_range`
result kind, so the contract enforces at record time what the report relies on at render time.
Recording is not computing, and the renderer is unchanged in that respect: it still formats
recorded values and derives none.

Two consequences are part of the design, not side effects. An ensemble manifest grows with the
path count, bounded by the `path_count` the ensemble already declares; per-scenario provenance is
therefore recorded once under `scenarios` and joined by scenario name rather than repeated on
every path row. And because the guaranteed-key check runs when a manifest is built rather than
when one is read, an ensemble manifest recorded before this amendment still verifies and still
renders — the report states plainly that it records no per-path ranges instead of filling them
in. That second half is the "render only what the summary records and say so plainly" option,
kept for the manifests that predate the change rather than discarded.

The contract's distributional-term check was deepened at the same time, for the kinds that
declare it: it now reaches nested key names, because a report renders a nested key as a visible
column heading and a top-level scan would clear a table whose headings claimed a percentile.

## Validation plan

- The four gates, unchanged: Ruff, mypy, pytest, clean wheel build, on Python 3.12, without
  secrets or official data.
- Rendering tests run entirely on synthetic manifests built from real module summaries (the
  contract's own test fixtures pattern), so CI exercises every kind without official data.
- A regression test renders a manifest for every kind in `RESULT_KINDS` and asserts the label,
  basis wording and standing exclusions appear adjacent to the figure block.
- A regression test asserts the landing-state report contains no numeric figure.
- Acceptance against real recorded runs (e.g. a manifest recorded from the accepted replay
  summary) is performed inside GitHub Actions where the artifacts live, following the standing
  operating constraint that live evidence steps are workflow dispatches.
